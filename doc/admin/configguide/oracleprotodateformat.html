Date Format

Oracle clients expect DATE columns to include the time of day, but an Oracle back-end's default date format usually drops it. To keep it, set the date_to_text_format parameter in the connection tag's connect string (see the Configuration Reference), for example:

<connection string="user=exampleuser;password=examplepassword;oracle_sid=ora1;date_to_text_format=YYYY-MM-DD HH24:MI:SS"/>

DATE columns are then returned in that format. How dates in queries are parsed is unaffected. Use a numeric, fixed-width format, with only /, -, . and : as delimiters, like the one above, or the date may not be parsed correctly.

TIMESTAMP columns have the same problem in a different form. An Oracle back-end's default timestamp formats usually have a 2-digit year, so a year outside of 1950-2049 comes back in the wrong century. To keep the century, also set the timestamp_to_text_format parameter (for TIMESTAMP and TIMESTAMP WITH LOCAL TIME ZONE columns) and the timestamp_tz_to_text_format parameter (for TIMESTAMP WITH TIME ZONE columns), for example:

<connection string="user=exampleuser;password=examplepassword;oracle_sid=ora1;date_to_text_format=YYYY-MM-DD HH24:MI:SS;timestamp_to_text_format=YYYY-MM-DD HH24:MI:SS.FF;timestamp_tz_to_text_format=YYYY-MM-DD HH24:MI:SS.FF TZH:TZM"/>

Use YYYY rather than SYYYY, as years BC are not supported. TIMESTAMP WITH TIME ZONE values must be printed with TZH:TZM. A value stored with a named time zone region is then sent to the client as its offset from UTC, as the region itself (TZR) can't be encoded.

Without these parameters, a 2-digit year is given a century using Oracle's RR rule, the same way the back-end would interpret it. Years 00-49 and 50-99 are taken to fall in the current century and the previous one (or the next one and the current one, during the second half of a century), so any year outside of that 100 year window is still returned in the wrong century.
