Password Verifier Type

Oracle authenticates with a challenge and response exchange. The server tells the client which kind of stored password verifier it has, and the client picks its cryptography and its session key size to match. Oracle 11g introduced the O5LOGON exchange, with one kind of verifier, and Oracle 12c added a second, stronger one. Before 11g there was O3LOGON, which uses DES rather than AES and a much smaller challenge.

The verifiertype option chooses which of the three the module offers. It accepts 9i, 11g or 12c. Rather than having a fixed default, it follows serverversion (see Server Version): 12c when serverversion is 12.1, and 11g when serverversion is 11.2. That's because a 12c verifier arrived with Oracle 12.1 and can't exist on an 11.2 database, and a client that is offered a combination no real server could have may refuse the login. Setting verifiertype to something the module doesn't recognize is the same as leaving it out.

9i is never the default. It is the O3LOGON exchange, which is what a client from before Oracle 10g speaks, and it is the only one such a client can answer at all - an OCI7 era client sent an O5LOGON challenge doesn't answer it, it drops the connection. Set it only for a deployment whose clients are that old, and note that it applies to every client of that listener: a modern client offered a 9i verifier can't log in either. Run a second listener if both kinds of client have to connect.

Setting 9i is a deliberate step down in security, and it is worth knowing what it costs. O3LOGON is built on DES and SHA-1 rather than AES and SHA-512, its password hash folds the case of the password, and anyone who can capture a login can attack the password offline. That was acceptable in 2002 and isn't now. It is offered because a client that old has no other way in, not because it is safe.

There is otherwise normally no reason to set it. The default already matches the version the module reports, and none of the modern clients tested against SQL Relay 2.3.0 needed it changed. Where one of them can't log in, it's the serverversion setting that decides it, not this one. The option is there so the 11g path stays reachable, for testing and for a client old enough to require it.

Note that this is not a setting about the back-end database. It describes only the challenge SQL Relay itself issues to its own clients, which SQL Relay's own authentication modules answer. It has no effect on how SQL Relay logs in to the back-end database.

<?xml version="1.0"?>
<instances>
	<instance id="example" dbase="oracle">
		<listeners>
			<listener protocol="oracle" port="1521" verifiertype="11g"/>
		</listeners>
		<connections>
			<connection string="user=scott;password=tiger;oracle_home=/u01/app/oracle/product/12.1.0;oracle_sid=ora1"/>
		</connections>
	</instance>
</instances>

An instance with a 9i listener needs one more thing: a back-end database of its own. A client old enough to speak OCI7 is too old to authenticate to the same modern database the other verifiertype settings talk to, so a 9i listener can't share a connections tag with an 11g or 12c one. Give it a separate instance, with its own connections tag pointing at a database old enough for the client to log in to.

The shape of that instance is otherwise ordinary: a listener tag with verifiertype="9i", and a connections tag pointing at the older backend, as shown below.

<?xml version="1.0"?>
<instances>
	<instance id="example9i" dbase="oracle">
		<listeners>
			<listener protocol="oracle" port="1522" serverversion="11.2" verifiertype="9i"/>
		</listeners>
		<connections>
			<connection string="user=scott;password=tiger;oracle_home=/u01/app/oracle/product/9.2.0;oracle_sid=ora2"/>
		</connections>
	</instance>
</instances>
