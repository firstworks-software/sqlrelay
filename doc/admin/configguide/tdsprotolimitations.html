Limitations

The implementation of the TDS protocol is likely sufficient for most applications, but it isn't 100% complete. Some notable limitations follow:

  • TLS/SSL mutual authentication requires a client that can present a client certificate. Not all clients can (eg. FreeTDS). See TLS/SSL Encryption and Authentication.
  • For odbc-backed instances, the connect string needs mars=yes for cursors and positioned updates to work. Without it, a query sent while another cursor still has rows pending fails with "Connection is busy with results for another command". See the SQL Relay Configuration Reference for the mars option.
  • Only TDS 5.0 and TDS 7.0 or later clients can log in. Older clients are refused, even though tdsversion accepts 420. TDS 5.0 clients that mix byte orders are also refused.
  • SAP's own password encryption (eg. Open Client's CS_SEC_ENCRYPTION) requires SAP's client libraries to be installed on the SQL Relay host. Without them, clients are asked to log in again without password encryption. This is unrelated to TLS/SSL encryption.
  • Bulk copy is supported, but each row is inserted separately, so it is no faster than individual inserts. It isn't supported for TDS 5.0 clients, or when a client sends it as a remote procedure call.
  • Positioned updates and deletes through a client-side cursor can only reach the first 1024 rows of a multi-row fetch. Past that, they fail with "The cursor is not on a row that can be updated". WHERE CURRENT OF queries aren't affected.
  • TDS 5.0 clients can't use the sp_cursorprepare, sp_cursoropen, sp_cursorexecute, sp_cursorprepexec or sp_cursorfetch procedures, or receive extremely wide result sets (more than 65535 columns). ----
