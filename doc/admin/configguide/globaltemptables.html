globaltemptables

The globaltemptables module simulates Oracle/DB2-style global temporary tables on databases (notably PostgreSQL) that only support session-local temporary tables.

In databases with global temporary tables, the table definition is permanent and visible to every session, but each session sees only its own rows. In databases with only session-local temporary tables, each session has to create the table itself, so an app that expects it to already exist fails. For each configured table, this module runs the table's create statement the first time a query references the table in each back-end session, so the table appears to be a global temporary table.

An example configuration:

<?xml version="1.0"?>
<instances>
	...
	<instance id="example" ... >
		...
		<querytranslations>
			<querytranslation module="normalize"/>
		</querytranslations>
		<triggers>
			<trigger module="globaltemptables" when="beforePrepare">
				<alreadyexists error="already exists"/>
				<table name="gtttest1">create temp table gtttest1 (id int primary key, value varchar(20))</table>
				<table name="gtttest2">create temp table gtttest2 (id int primary key, value varchar(20))</table>
			</trigger>
		</triggers>
		...
	</instance>
	...
</instances>

In this example...

The trigger runs before the query is prepared. This is the only useful setting for when, since the table has to exist before the database prepares a query that uses it.

Two tables are configured, gtttest1 and gtttest2. The first time either one is referenced in a back-end session, by any kind of query, its create statement is run.

The create may fail because the table already exists. The alreadyexists tag tells the module which errors mean that, so they can be treated as success. It supports two attributes, error and sqlstate. If either one matches, the create is treated as success.

The error attribute may be set to either:

  • a numeric value - matched against the database error number
  • a string - matched as a substring against the database error text

Error text varies with the database's locale, and some databases (eg. PostgreSQL) report the same error number for every error, so sqlstate is usually more reliable. It is a 5-character SQLSTATE code, matched exactly but without regard to case, and is checked before error. If it isn't set, it defaults to 42P07 for PostgreSQL and 42S01 for MySQL/MariaDB. Other databases have no default. Set it to an empty string to disable the default. Not every database reports a SQLSTATE. For those, only error is checked.

If the create fails and neither the sqlstate nor the error check matches, that error is reported back to the client as if the user's query had failed.

On PostgreSQL, the module also adds if not exists to the create statement, unless it's already there. Otherwise, a failed create would abort the surrounding transaction, even if alreadyexists treats it as success. This is based on the real back-end database, not on the identity connect string parameter.

The trigger matches the table name as a whole word anywhere in the query, and assumes the query has already been normalized.

Note that in this example, the normalize query translation is loaded prior to the globaltemptables trigger. Pattern matching is substantially more reliable and efficient if the query has been normalized first. See the normalize query translation for more information.

The trigger tag supports the following attributes in addition to the standard module, when, enabled, and debug attributes:

  • none beyond the nested alreadyexists and table tags described above

The table tag supports the following attribute:

  • name
    • the name of the table to watch for - matched, as a whole word, against every query at prepare time
    • the table body (between the open and close tags) is the create statement to run on the backend session the first time the table is referenced

The body of the table tag may also use the [...filename...] syntax supported elsewhere in the SQL Relay config to read the create statement from an external file - useful for long create statements.

Considerations

Because the table name is matched anywhere in the query, a query that only mentions it in a string literal or comment also causes the table to be created. This is harmless.

After creating a table, the module assumes it exists until the sqlr-connection process is recycled, the client session ends, or the transaction is rolled back. After that, it runs the create statement again the next time the table is referenced.

Each sqlr-connection process has its own copy of the table, so rows inserted through one aren't visible through another, just as with a real global temporary table.
