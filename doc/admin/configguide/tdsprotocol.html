TDS Protocol

SQL Relay can be configured to speak the native TDS protocol, enabling client programs for Microsoft SQL Server and SAP/Sybase (eg. the tsql command line program) to access SQL Relay directly.

If an instance speaks the TDS client-server protocol, then any client that wishes to use it must also speak the TDS client-server protocol. This means that most software written using the FreeTDS or Microsoft SQL Server APIs, or written using a database abstraction layer which loads a driver for Microsoft SQL Server or SAP/Sybase can access this instance. However, it also means that SQL Relay's standard sqlrsh client program and client programs for other databases (eg. the mysql, psql, and sqlplus command line programs, MySQL Workbench, Oracle SQL Developer, etc.) cannot access this instance.

Unlike the Oracle protocol module, the TDS protocol module is complete for query execution, including TLS/SSL encryption and authentication. Clients log in, run queries, and read result sets, and most of the module's configuration doesn't need documenting because the defaults work. The sections below cover the options that do - notably the version and packet size that the module negotiates, which is what compatibility with a particular client usually turns on.

Compatibility has been verified in SQL Relay's own test suite against FreeTDS, using both its ct-lib API and its tsql command line program, and separately against SAP/Sybase's own Open Client (ct-lib), which is how the pre-TDS7 (TDS 5.0) login path is exercised. Since TDS is a standard protocol, other MS-TDS-speaking clients and drivers - isql, sqlcmd, jTDS, and similar - should also work, but they haven't been tested in-tree.

Basic Configuration

To enable SQL Relay to speak the TDS protocol, add the appropriate listener tag:

<?xml version="1.0"?>
<instances>
	<instance id="example" dbase="odbc">
		<listeners>
			<listener protocol="tds" port="1433"/>
		</listeners>
		<connections>
			<connection string="dsn=mssqlodbc;user=example;password=example;mars=yes"/>
		</connections>
	</instance>
</instances>

In this configuration:

  • The listener tag instructs SQL Relay to load the tds protocol module, and listen on port 1433, which is the standard Microsoft SQL Server port.
  • The connection tag instructs the instance to log in to the mssqlodbc ODBC data source as user example with password example.

Note the mars=yes parameter in the connect string. See the SQL Relay Configuration Reference for the mars option, which instances using the tds protocol typically need.

The instance can be started using:

sqlr-start -id example

and accessed from the local machine using:

tsql -H localhost -p 1433 -U example -P example

The instance can be stopped using:

sqlr-stop -id example

Listener Options

In the example above, the instance is configured to listen on port 1433, which is already the standard Microsoft SQL Server port, so no special port choice is needed.

If the server has multiple network interfaces, SQL Relay can also be configured to listen on specific IP addresses.

<?xml version="1.0"?>
<instances>
	<instance id="example" dbase="odbc">
		<listeners>
			<listener protocol="tds" addresses="192.168.1.50,192.168.1.51" port="1433"/>
		</listeners>
		<connections>
			<connection string="dsn=mssqlodbc;user=example;password=example;mars=yes"/>
		</connections>
	</instance>
</instances>

In the example above, it can be accessed on 192.168.1.50 and 192.168.1.51 but not on 127.0.0.1 (localhost).

It can also be configured to listen on a unix socket by adding a socket attribute to the listener tag.

<?xml version="1.0"?>
<instances>
	<instance id="example" dbase="odbc">
		<listeners>
			<listener protocol="tds" port="1433" socket="/tmp/tds.socket"/>
		</listeners>
		<connections>
			<connection string="dsn=mssqlodbc;user=example;password=example;mars=yes"/>
		</connections>
	</instance>
</instances>

( NOTE: The user that SQL Relay runs as must be able to read and write to the path of the socket.)

If the socket option is specified but the port option is not, then SQL Relay will only listen on the socket. If port and socket options are both specified then it listens on both.

TDS Version

A TDS client works out how to read the server's answers from the version of the protocol it believes is in use. Field widths and message layouts vary between versions, so client and server have to agree.

By default, SQL Relay guesses the version from the back-end database's version string. "SQL Server 2012" and later map to TDS 7.4, "SQL Server 2008 R2" to TDS 7.31, and so on down to "SQL Server 6." at TDS 4.2. When the version string can't be mapped - which happens with a back-end that isn't Microsoft SQL Server at all, or one whose version string the module doesn't recognize - SQL Relay falls back to whatever version the connecting client itself requests, rather than to a fixed default. Falling back to an old version instead can hang some clients, because they don't always reconsider the field widths they asked for.

The tdsversion attribute on the listener tag overrides the guess. It accepts a TDS version number as a plain decimal integer, in the form the protocol uses internally: 420 (TDS 4.2), 500 (5.0), 700 (7.0), 710 (7.1), 711 (7.1 SP1), 720 (7.2), 730 (7.3), 731 (7.31), or 740 (7.4). Leaving it out, or setting it to 0, means auto-detect.

<?xml version="1.0"?>
<instances>
	<instance id="example" dbase="odbc">
		<listeners>
			<listener protocol="tds" port="1433" tdsversion="740"/>
		</listeners>
		<connections>
			<connection string="dsn=mssqlodbc;user=example;password=example;mars=yes"/>
		</connections>
	</instance>
</instances>

The version matters for more than field widths. Clients such as FreeTDS only send a PRELOGIN packet - the packet where encryption is negotiated - when using TDS 7.1 or later. Below that, the client skips straight to the login packet, and any encryption settings configured on the client are silently never applied. That is a property of the client, not of SQL Relay.

So if the back-end's version string can't be mapped, and the client's own default version is low, no PRELOGIN negotiation happens at all. Setting tdsversion to 710 or higher is what makes it happen. See TLS/SSL Encryption and Authentication below.

Packet Size

TDS sends data in packets of a fixed size, which the client and server negotiate during login. Larger packets mean fewer round trips for large result sets, and smaller packets can suit a constrained network or a client that can't handle large ones.

The packetsize attribute on the listener tag sets the packet size, in bytes, that SQL Relay uses until a connecting client negotiates a different size. It defaults to 4096. It must not exceed maxpacketsize; if it does, SQL Relay clamps it.

The maxpacketsize attribute sets the largest packet size, in bytes, that a connecting client is allowed to negotiate. It defaults to 65535, which is also the largest value allowed. Setting it to 0, or to anything above 65535, is the same as setting it to 65535.

A client that asks to negotiate a packet size below 512 bytes is refused; the connection keeps using whatever packet size was already negotiated.

<?xml version="1.0"?>
<instances>
	<instance id="example" dbase="odbc">
		<listeners>
			<listener protocol="tds" port="1433" packetsize="2048" maxpacketsize="32767"/>
		</listeners>
		<connections>
			<connection string="dsn=mssqlodbc;user=example;password=example;mars=yes"/>
		</connections>
	</instance>
</instances>

Authentication/Encryption Options

When using the TDS protocol, there are several options for controlling which users are allowed to access an instance of SQL Relay.

Connect Strings Auth

The default authentication option is connect strings auth.

When connect strings authentication is used, a user is authenticated against the set of user/password combinations that SQL Relay is configured to use to access the database. That is, they are the values of the user and password parameters of the string attribute of the connection tag.

The basic configuration example above uses this option. SQL Relay is configured to access the database using example/example credentials, so clients would also use example/example credentials to access SQL Relay.

Though it is not necessary, it is possible to explicitly configure SQL Relay to load the connect strings auth module as follows:

<?xml version="1.0"?>
<instances>
	<instance id="example" dbase="odbc">
		<listeners>
			<listener protocol="tds" port="1433"/>
		</listeners>
		<auths>
			<auth module="tds_connectstrings"/>
		</auths>
		<connections>
			<connection string="dsn=mssqlodbc;user=example;password=example;mars=yes"/>
		</connections>
	</instance>
</instances>

User List Auth

Another authentication option is user list auth.

When user list authentication is used, a user is authenticated against a static list of user/password combinations, which may be different than the user/password used that SQL Relay uses to access the database.

To enable user list auth, you must provide a list of user/password combinations, as follows:

<?xml version="1.0"?>
<instances>
	<instance id="example" dbase="odbc">
		<listeners>
			<listener protocol="tds" port="1433"/>
		</listeners>
		<auths>
			<auth module="tds_userlist">
				<user user="oneuser" password="onepassword"/>
				<user user="anotheruser" password="anotherpassword"/>
				<user user="yetanotheruser" password="yetanotherpassword"/>
			</auth>
		</auths>
		<connections>
			<connection string="dsn=mssqlodbc;user=example;password=example;mars=yes"/>
		</connections>
	</instance>
</instances>

When using SQL Relay as a transparent proxy, it is desirable to define the same set of users that are defined in the database itself. While this may sound inconvenient, in practice, most apps use a single user to access the database, and it's not uncommon for multiple apps to share a user. So, the list is typically short.

The tds_userlist module compares the user and password sent by the client directly against the configured list - there is no challenge/response step to negotiate, unlike the Firebird or Oracle protocols.

TLS/SSL Encryption and Authentication

SQL Relay supports TLS/SSL encryption and authentication between the TDS client and SQL Relay server.

When TLS/SSL encryption and authentication is used:

  • Communications between the TDS client and SQL Relay server are encrypted.
  • TDS clients may optionally validate the server's certificate and identity.

When using TLS/SSL encryption and authentication, at minimum, the SQL Relay server must be configured to load a certificate. For highly secure production environments, this certificate should come from a trusted certificate authority. In other environments the certificate may be self-signed, or even be borrowed from another server.

Encryption Only

The following configuration enables TLS/SSL encryption for an instance of SQL Relay:

<?xml version="1.0"?>
<instances>
	<instance id="example" dbase="odbc">
		<listeners>
			<listener protocol="tds" port="1433" tls="yes" tlscert="/usr/local/firstworks/etc/sqlrserver.pem"/>
		</listeners>
		<connections>
			<connection string="dsn=mssqlodbc;user=example;password=example;mars=yes"/>
		</connections>
	</instance>
</instances>
  • The tls attribute enables (or disables) TLS/SSL encryption.
  • The tlscert attribute specifies the TLS/SSL certificate chain to use.
    • (a .pem file is specified in this example, but on Windows systems, a .pfx file or Windows Certificate Store reference must be used. See The tlscert Parameter for details.)
    • If the file specified by tlscert doesn't already include the private key, the tlskey attribute may be used to specify a separate file containing it.

TDS negotiates encryption in the PRELOGIN exchange, before the login is sent, and the module answers with what the client asked for:

  • A client that requires encryption gets the whole session encrypted.
  • A client that is merely willing to encrypt gets only its login encrypted. The rest of the session runs in the clear. This is what a Microsoft SQL Server does by default, and what most TDS clients ask for unless they are configured otherwise.
  • A client that says it doesn't support encryption, or that omits the encryption option entirely, isn't pushed into a handshake it never offered. Its login is refused with a "TLS required" error instead.

Which of these a client asks for is a client-side setting. With freetds, for example, it is the encryption setting in freetds.conf, and a client that validates the server's certificate also needs a ca file there.

Mutual Authentication

The tlsvalidate and tlsca attributes described for the other protocols are honored by the TDS module as well, and enable mutual authentication - the server requests and validates a certificate from the client. Note, though, that the freetds client cannot present a client certificate, so mutual authentication can only be used with clients that can.

Performance Considerations

While TLS/SSL authenticated and encrypted sessions are substantially more secure than standard SQL Relay sessions, several factors contribute to a performance penalty:

  • When establishing the secure session, a significant amount of data must be sent back and forth between the client and server over multiple network round-trips.
  • Some TLS/SSL implementations impose a limit on the amount of data that can be sent or received at once, so more round trips may be required when processing queries.
  • Without dedicated encryption hardware and a TLS/SSL implementation that supports it, the computation involved in encrypting and decrypting data can also introduce delays.

Any kind of full session encryption should be used with caution in performance-sensitive applications.

Foreign Backend

Since SQL Relay supports a variety of database back-ends, the app can also be redirected to any of these databases, instead of the Microsoft SQL Server or SAP/Sybase database it was originally written to use.

This is as simple as specifying a different database using the dbase attribute in the instance tag and specifying the appropriate database connection string in the string attribute of the connection tag.

<?xml version="1.0"?>
<instances>
	<instance id="example" dbase="oracle">
		<listeners>
			<listener protocol="tds" port="1433"/>
		</listeners>
		<connections>
			<connection string="user=scott;password=tiger;oracle_sid=ora1"/>
		</connections>
	</instance>
</instances>

In this example, a TDS front-end provides TDS applications access to an Oracle back-end database.

Depending on the back-end, it might also be necessary to make some other configuration changes, as well, for example:

  • In the instance tag:
    • set translatebindvariables="yes"
    • set the isolationlevel attribute
    • set transactionmodel="explicit"
  • In the string attribute of the connection tag:
    • set autocommit=yes or autocommit=no
    • implement a function that returns the last insert id and specify it using the lastinsertidfunction parameter
    • set the identity parameter to override the database type
    • set ignorespace=yes
    • set the overrideschema parameter
    • set the typemangling and/or tablemangling parameters
  • use Query Translation modules
  • use Result Set Translation modules
  • use Error Translation modules
  • use Session Queries

In your app, it might stil be necessary to modify some queries to use the syntax of the foreign database, or even update some code, but a full rewrite of the app should not be necessary.

Limitations

The implementation of the TDS protocol is likely sufficient for most applications, but it isn't 100% complete. Some notable limitations follow:

  • TLS/SSL mutual authentication requires a client that can present a client certificate. The freetds client cannot. See TLS/SSL Encryption and Authentication above.
  • For odbc-backed instances, the connect string needs mars=yes for cursors and positioned updates to work. Without it, a query sent while another cursor still has rows pending fails with "Connection is busy with results for another command". See the SQL Relay Configuration Reference for the mars option.
  • TDS 5.0 is the only pre-TDS7 dialect a client can actually log in with. A client that declares an older dialect (4.2, 4.6, or 4.9.5) is refused with an error, even though some of those are otherwise legal values for the tdsversion listener option.
  • A pre-TDS7 login that declares more than one byte order for integers, floats and datetimes is refused.
  • A TDS-native encrypted login (SEC_LOGPWD/CS_SEC_ENCRYPTION) requires a password cipher that SQL Relay loads from SAP's own libsybcomn64 library on the SQL Relay host; if that library isn't installed, or doesn't provide the cipher, the module refuses the login and asks the client to disable password encryption and log in again. This is separate from, and unrelated to, TLS/SSL encryption.
  • Bulk copy ("insert bulk") is supported, but not as a true bulk load: each incoming row becomes its own INSERT statement and its own round trip to the back-end database, rather than one round trip for the whole batch. It is also not supported at all when sent as an RPC, or under the TDS 5.0 (pre-TDS7/ct-lib) dialect.
  • A positioned update or delete issued as a numbered cursor operation (sp_cursor, or the TDS 5.0 curupdate/curdelete tokens) can only see the first 1024 buffered rows of a multi-row fetch. Positioning past that limit fails with "The cursor is not on a row that can be updated". This cap doesn't apply to an ordinary WHERE CURRENT OF sent as a plain query, which is handled by the back-end database's own cursor instead.
  • A few TDS 5.0 (pre-TDS7/ct-lib) edge cases aren't implemented: the sp_cursorprepare, sp_cursoropen, sp_cursorexecute, sp_cursorprepexec and sp_cursorfetch numbered cursor procedures sent as RPCs (sp_cursor and sp_cursorclose work normally), the "procname" dynamic-SQL type, and a result set wider than 65535 columns or with more than 65535 bytes of metadata.
